某运动app登录接口逆向分析

发表于2026-04-08|更新于2026-04-08|安卓
|总字数:1.4k|阅读时长:6分钟|浏览量:

设备：Pixel 4 (Android 10, Magisk root)

app版本：2.9.x

目标

完全脱离 APP，写Python脚本构造合法的登录请求，拿到服务端返回的 token。

  • 思路

先抓包看username和password是否有加密，以及签名字段，然后追溯各签名字段计算逻辑以及加密字段的加密逻辑，并控制变量排除后端没有校验的字段。

过程

抓包

使用socksTun转发+mitm(SOCKS5代理)抓包发现抓不到，猜测有ssl pin，由于内核版本过低没法拿ecapture试，只能去找网络通信逻辑代码。

解包apk，发现有壳

.xml里面找到入口类

吾爱上查了下，说是顶象加固(claude说是几维?)

运行app，用P4nda0s/panda-dex-dumper dump 出dex，重新用jadx分析并导出在工作目录

发现用了okhttp3库，拿frida过一下，但是有frida检测

  • 遍历每个服务的进程名，检查是否包含”frida”

  • 端口检测和其它检测

换个端口以及把frida-server改成fs即可

最后发现是默认不信任用户证书，只需要hook 替换为信任所有证书就能抓到包：(赶紧安装一个MagiskTrustUserCerts..)

抓到的包信息如下

username是明文，password有加密，看起来像base64，解码后发现是十六字节内容，应该还有一层加密。

两个签名字段v1和User-Agent，重放发现后端不校验v1，只需逆向sign的生成逻辑

分析关键字段生成逻辑

password

搜索password定位到输入框逻辑

追踪password加密调用链

C0723.m4606()是拼接了一些常量返回一个key

处理逻辑在native层，有混淆，暂时走不通

根据password被加密成16字节，猜测是AES

回头发现net.crigh.api.encrypt.ChingoEncrypt类有调用native层aes加密的逻辑

猜测可能调用了这里的加密，于是选择hook 这个方法和java标准AES库，观察它用了谁

触发登录，输出

cgapiAESEncrypt 没有被调用，Cipher.doFinal 被调用了。确认密码加密走的是标准 Java AES。

再 hook Cipher.init 拿密钥：

  • mode=1 → Cipher.ENCRYPT_MODE
  • key hex 36643331323162363530653432383535 → ASCII 6d3121b650e42855（16 字节）
  • Cipher.init(mode, key) 没有传 IV → ECB 模式
  • 解密还原得到password
  • 密文与抓包完全匹配

sign

看sign长得像md5，直接hook 所有MD5调用，虽然壳混淆了类名，最终都要调用 java.security.MessageDigest（MD5/SHA256）和javax.crypto.Cipher（AES）。

部分输出：

定位到计算各字段的逻辑

C0713.m4566() 读取 SP("key_v1")，为空则用 System.currentTimeMillis()，传给 C0714.m4572()（原名 MD5Util.java），最终调用标准 MessageDigest.getInstance("MD5")。

[MD5 FULL]中包含了请求体里除app_key以外的所有内容，以及一个硬编码的密钥262b6c001ea05beceb9d560be1dbf14f，它被拆成多个硬编码字符串和 string resource 分散存储，运行时拼接。

md5计算后发现和sign值一致

总结

app是32位的，版本比较老，经常闪退

壳代码有MBA和控制流平台化混淆
